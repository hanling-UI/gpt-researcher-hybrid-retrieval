# 项目说明（一页纸）

> 基于 [gpt-researcher](https://github.com/assafelovic/gpt-researcher) 的二次开发。
> 目标是**在不砍掉原有功能的前提下**，把 RAG 检索链路做成工业级的四段式：
> 数据清洗 → 混合召回 → RRF 融合 → 精排截断。

仓库：https://github.com/hanling-UI/gpt-researcher-hybrid-retrieval
（演示实例在线，需访问口令；口令用于控制 API 成本，联系获取）

---

## 1. 要解决的问题

上游默认把抓回来的网页**整段塞进上下文**，或者只用单一检索通道（关键词或向量）。结果是：

- token 消耗高（全量约 2.5 万字符），大部分是导航栏、页脚、重复转载；
- 关键词检索对同义表达无能为力，向量检索对专有名词、型号、版本号不敏感；
- chunk 不做尺寸控制，精排模型会**静默截断**超长输入，后半截根本没参与排序。

所以做了四件事，每一件都对应一个可验证的指标。

## 2. 四个改造点

| # | 改造 | 落点 | 解决什么 |
|---|---|---|---|
| 1 | **数据清洗增强** | `gpt_researcher/scraper/cleaning.py` | 模板行、跨页重复、元信息块、分块近似重复 |
| 2 | **混合检索** | `context/tokenize.py` + `context/hybrid.py` | BM25(jieba) 与向量双路召回，互补字面/语义 |
| 3 | **手写 RRF** | `context/hybrid.py::rrf_fuse` | 只用名次融合，绕开分数归一化 |
| 4 | **Rerank 重排** | `context/rerank.py` | Top20 → 重排模型 → **Top3** 送入写作模型 |

## 3. 关键决策与理由

**为什么用 RRF 而不是加权分数相加？**
BM25 分数无上界（可以到 20+），余弦相似度在 [-1,1]，量纲与分布都不同。相加必须先归一化或学权重，而学权重需要标注数据。RRF 只问"你在这条路排第几"，天然免疫量纲问题，零训练成本。

**k=60 是什么？**
`1/(k+rank)` 里的平滑项。k 越大，名次衰减越平缓，更信任"两路都提过"的共识；k 越小越偏向头部。60 是原论文经验值，实践 40~80 都常见。

**为什么 chunk 是 500 / 重叠 80？**
精排模型输入上限 512 token，中文基本 1 字≈1 token，超过会被**静默截断**（不报错，只是后半段没参与打分）。重叠 80 保证答案压在切点上时至少有一块完整。

**为什么清洗不用 NFKC？**
NFKC 会把中文全角标点（，：（））转成半角，破坏中文排版，而且这些正文最终要进提示词。所以只做全角字母数字、零宽字符、空白的修正。

**为什么不用 faiss / chroma 做持久索引？**
单次研究候选块只有几十到几百，内存里算 BM25 和余弦是毫秒级；引入向量库只会增加镜像体积与冷启动时间，这个量级下收益不明显。

**jieba 缺失时为什么降级成二元组？**
原来的正则 `\w+` 会把整句中文切成一个 token，导致 BM25 对中文**恒为 0 分**——不报错，只是"关键词检索"静默失效。降级成汉字二元组至少还能匹配，是可解释的退化，不是无声的失效。

## 4. 效果（固定语料回放，5 查询平均，预算对齐 2000 字符）

| 模式 | 平均字符 | 语义覆盖 | 平均耗时 |
|---|---|---|---|
| none（全量） | 25492 | 0.712 | — |
| keyword（上游） | 9937 | 0.733 | 0.21s |
| embeddings | 10001 | 0.742 | 15.16s |
| hybrid | 1721 | 0.755 | 1.86s |
| **hybrid + rerank** | **1703** | **0.764** | 2.56s |

- 上下文压缩 **93%**（25492 → 1703 字符）
- 语义覆盖 0.712 → 0.764，5 个查询均不低于上游
- **诚实结论**：重排相对 hybrid 只有 +0.009（2/5 略优、3/5 持平），样本量 5 个查询，方向正确但幅度有限；候选池只有 20~85 块时 RRF 已足够好

复现方式见 [EVAL.md](../EVAL.md)，语料在 `eval_runs/`。

## 5. 工程化部分（不只是算法）

- **WebSocket 流式**：研究进度逐条推送；25s 心跳 + 断线重连去重，避免追问刷屏
- **无状态导出**：PDF/Word 改为「提交任务 → 轮询 → 取文件」，规避免费实例渲染数分钟导致的请求超时
- **Word 预览页**：浏览器不能渲染 docx，把同一份正文渲染成网页，顶部可下载原件 / 打印存 PDF
- **会话侧边栏**：新建 / 切换 / 删除 / 搜索，会话存 localStorage + 服务端 JSON 双份
- **部署**：精简 Dockerfile（去掉浏览器、装 CJK 字体）+ Render 免费层，README 写了完整环境变量
- **测试**：`tests/test_retrieval_hybrid.py` 22 个离线用例，覆盖分词、BM25、RRF 公式、切块、清洗去重

## 6. 已知限制

- PDF 由 WeasyPrint 在 0.1 核 CPU 上渲染，首次 1~3 分钟
- 免费层无持久磁盘，服务端会话文件在重新部署后清空（浏览器那份不受影响）
- 评测样本仅 5 个查询，只反映趋势，不足以做显著性结论
- 上游 CI 的 `imports` 作业失败是遗留问题（`logger.py` 顶层 `import click`，requirements 未声明，setup.py 又排除了 uvicorn），与本二创无关

## 7. 怎么验证

```bash
# 离线评测（首次抓取并落盘，之后只换排序策略）
python eval_context.py --collect
python eval_context.py

# 本地起服务
cp .env.example .env    # 填入自己的 OPENAI_API_KEY / TAVILY_API_KEY

```

本地界面上完整走一遍：输入问题 → 看进度 → 报告 → 侧边栏切会话 → 追问 → 导出 Word / Markdown / JSON。
